# WP-02 — Dependency & API spike report (M0)

**Authority:** per LM-ARCH-001 §22.1 (M0 exit criteria) this report **replaces §6.5**
("Libraries `[UNVERIFIED]`"). Every value below was captured live from the package
registries on **2026-10-04** (raw evidence: `evidence/wp02-registry-capture-2026-10-04.json`
and `evidence/raw-2026-10-04/`). No version was typed from memory (AGENTS.md).

**Capture method & limitations (read first):**

- PyPI: live `GET https://pypi.org/pypi/<pkg>/json` per package. npm: live
  `GET https://registry.npmjs.org/<pkg>`. Both returned 200; raw JSON archived.
- **GitHub REST API: HTTP 403 (rate limit) for every repository** from this
  environment. Repo-level activity (pushed_at, open issues, GitHub releases) is
  therefore **not captured**. Maintenance signals here = registry publish dates +
  README content. A repo-activity pass is listed in "Not verified".
- Android 16/17 compatibility: no candidate library's README states any
  Android-16/17 / targetSdk-36/37 claim. "No evidence found" is recorded as-is;
  §6.4's local-network permission rules remain the governing facts, and runtime
  verification belongs to M2/M3 (WP-09/WP-11), not M0.

**License note (CON-03):** `zeroconf` is LGPL-2.1-or-later — the only Agent
dependency that is not permissive. Using it as an unmodified installed library is
standard LGPL library usage; flagging for owner awareness alongside Q-08 (project
license). Replacing it with a permissive-licensed mDNS implementation would need a
new ADR and has no mature Python alternative today.

**pynvml vs nvidia-ml-py (§6.5-adjacent finding):** PyPI today has `pynvml` 13.0.1
(2025-09-05, BSD-3, https://pypi.org/pypi/pynvml/json) and `nvidia-ml-py` 13.615.71
(2026-09-25, BSD, https://pypi.org/pypi/nvidia-ml-py/json — NVIDIA's
forums.developer.nvidia.com project page). §21.2 names `pynvml`; it is kept as the
optional `nvidia` extra. If M5 finds `nvidia-ml-py` is the better-supported
distribution, switching = new dependency → ADR at that time.

## 2. React Native candidates (§6.5 items)

Architectural constraint from ADR-003 (binding): the Kotlin `mesh-core` module
owns "pinned-TLS HTTP + SSE streaming" and "the JS layer never performs raw
network I/O to Agents". So for the **Mesh API path**, any JS-side SSE or HTTP
library cannot carry pinning — the native module is mandatory regardless of
library quality. The verdicts below apply that constraint.

## 3. Android 16/17 compatibility (§6.5 explicit question)

**No candidate library README or registry metadata states Android 16/17 /
targetSdk 36/37 compatibility** (grep of captured READMEs: zero hits; evidence
JSON records this). Per §6.4 the governing facts are the OS rules themselves
(NEARBY_WIFI_DEVICES on 16; mandatory `ACCESS_LOCAL_NETWORK` at targetSdk 37 on
17). Runtime compatibility testing is scheduled where it can actually be
executed: WP-09 (mesh-core, M2) and WP-11 (mDNS, M3). This report records the
absence of evidence rather than inventing it.
